# WALT VPN node (Raspberry Pi 5B) boot — diagrams

> Branch: `etienne-dev`. These diagrams describe how a WALT VPN-capable
> Raspberry Pi 5B boots, and how the server prepares/exposes the boot material.
>
> Key source references:
> - `server/walt/server/mount/setup.py` → `generate_boot_sig()`, `setup()`
> - `server/walt/server/exports/exports.py`, `server/walt/server/exports/ops/mounts.py`
> - `server/walt/server/processes/main/network/tftp.py`

> - `server/walt/server/processes/main/vpn.py` → `enrollment()`
> - `server/walt/server/setup/vpn.py`

## 1. Deployment context

```mermaid
flowchart LR
    SRV["WalT server<br/>walt-server-daemon<br/>walt-server-httpd<br/>DHCP / TFTP / NFS / NBD<br/>VPN CA + HTTP boot keys"]

    subgraph site1["Site A : walt-net (local VLAN)"]
        N1["Node 1 (RPi5)"]
        N2["Node 2 (RPi5)"]
    end

    subgraph site2["Site B : remote (moved / distant)"]
        N4["Node 4 (RPi5)<br/>VPN node"]
    end

    subgraph ep["Optional remote entrypoint"]
        EP["HTTP / SSH entrypoint<br/>(proxy reachable from Internet)"]
    end

    SRV ---|"walt-net (DHCP/TFTP/NFS)"| N1
    SRV ---|"walt-net"| N2
    SRV <-->|"HTTP 80 / SSH 22"| EP
    EP <-->|"HTTP / SSH (through corporate network / Internet)"| N4
    EP --- N1
    EP --- N2
```

Notes:
- VPN nodes can boot **either** on `walt-net` **or** through an HTTP/SSH
  entrypoint (usually the server itself, by default).
- The VPN is limited to Raspberry Pi 5B boards (`rpi-5-b`).
- On `walt-net`, HTTP traffic to any VPN HTTP entrypoint is caught by the
  server's own `WALT-DNAT` chain and handled locally
  (`processes/main/vpn.py::prepare/update_vpn_dnat`).

## 2. Server side: mounting an OS image, signing the bootable FAT image and exposing it

This answers *"when the server signs the bootable FAT image (i.e. when the OS
image is mounted and exposed on the network for booting)"*.

Mermaid sequence of what happens **before** a node can boot, triggered when the
daemon reconciles exports (at startup, or when a node's image assignment /
registration changes and the image must be mounted):

```mermaid
sequenceDiagram
    autonumber
    participant WF as "Exports workflow<br/>(exports.py / ops/mounts.py)"
    participant MM as "Image mount<br/>(mount/mount.py)"
    participant SETUP as "Image setup<br/>(mount/setup.py)"
    participant FS as "Mount point<br/>/var/lib/walt/images/<id>/fs"
    participant NFS as "NFS export / TFTP / boot dir"
    participant HTTP as "walt-server-httpd (HTTP boot)"

    Note over WF: daemon (re)start, node image assignment<br/>or first-node registration
    WF->>WF: compute MOUNT-IMAGE <image_id> <size> directives
    WF->>MM: mount image (buildah container)
    MM->>FS: mount container filesystem<br/>at images/<id>/fs
    MM->>SETUP: setup(image_id, mount_path, size)
    SETUP->>SETUP: write walt scripts, ssh host keys,<br/>resolv.conf, fix symlinks, timezone...
    SETUP->>SETUP: generate_boot_sig(mount_path)
    Note right of SETUP: if boot/rpi-5-b/boot.img exists<br/>AND boot.sig missing
    SETUP->>SETUP: sha256 = dgst -sha256(boot.img)
    SETUP->>SETUP: rsa2048 = dgst -sign private.pem(boot.img)
    SETUP->>SETUP: ts = now()
    SETUP->>FS: write boot/rpi-5-b/boot.sig<br/>(sha256 / ts / rsa2048)
    SETUP-->>MM: done
    MM-->>WF: mounted
    WF->>NFS: export images/<id>/fs (NFSv3)
    WF->>NFS: symlink nodes/<ip>/fs -> image fs<br/>nodes/<ip>/tftp -> image /boot/<model>
    Note over HTTP: At node boot time (later), the RPi firmware<br/>fetches boot.img + boot.sig over HTTP
    Node->>HTTP: GET /walt-vpn/per-ip/<ip>/boot.img
    Node->>HTTP: GET /walt-vpn/per-ip/<ip>/boot.sig
    HTTP->>FS: serve from nodes/<ip>/tftp (static file)
    FS-->>Node: boot.sig (signed FAT boot image)
```

Key points:
- The signature is computed **once at mount time** and stored as a static
  `boot.sig` next to `boot.img` in the image boot directory
  (`mount/setup.py:210-229`). This differs from `master`, where `boot.sig`
  used to be computed on-the-fly on each HTTP request.
- The HTTP boot keys are an RSA-2048 key pair at
  `/var/lib/walt/http-boot/private.pem` + `public.pem` (`const.py`,
  generated by the server). `public.pem` is what the board ultimately stores
  in its EEPROM to verify `boot.sig`.
- `boot.img` is a FAT image (kernel + initramfs) that **contains no secrets**,
  hence it is safe over plain HTTP.

## 3. First boot: enrollment & secrets provisioning into the EEPROM

Sequence for a fresh RPi5 board connecting so that it gets enrolled as a VPN
node and stores the VPN secrets in its EEPROM:

```mermaid
sequenceDiagram
    autonumber
    participant R as "RPi5 board (firmware + initramfs)"
    participant EP as "HTTP/SSH entrypoint"
    participant HTTP as "walt-server-httpd"
    participant DAEMON as "walt-server-daemon<br/>(vpn.enrollment)"
    participant CA as "VPN CA key (vpn-ca-key)"
    participant DB as "database<br/>(vpnnodes / vpnauth)"
    participant DHCP as "dhcpd"

    R->>EP: power-on, HTTP boot: fetch boot.img + boot.sig
    EP->>HTTP: redirect /walt-vpn/per-ip/<ip>/...
    HTTP-->>R: boot.img + boot.sig
    Note over R: firmware verifies boot.sig with server pubkey<br/>(not yet in EEPROM on really first boot)
    R->>R: run initramfs (from boot.img)

    R->>HTTP: POST /walt-vpn/enroll + ssh pubkey
    HTTP->>DAEMON: enrollment(node_ip, pubkey)
    DAEMON->>DAEMON: check node is a rpi-5-b on walt-net<br/>+ entrypoints configured
    DAEMON->>CA: ssh-keygen -s VPN_CA_KEY<br/>sign node pubkey (-n walt-vpn)
    CA-->>DAEMON: pubkeycert (SSH certificate)
    DAEMON->>DB: generate vpnmac (52:54:00...)<br/>INSERT vpnnodes(mac, vpnmac)<br/>INSERT vpnauth(vpnmac, pubkeycert)
    DAEMON->>DHCP: update dhcpd to recognize vpnmac
    DAEMON-->>HTTP: status OK
    HTTP-->>R: enrollment accepted

    R->>HTTP: GET node-conf/ssh-pubkey-cert
    R->>HTTP: GET node-conf/ssh-entrypoint-host-keys
    R->>HTTP: GET node-conf/vpn-mac
    R->>HTTP: GET node-conf/ssh-entrypoint
    R->>HTTP: GET node-conf/http-entrypoint
    R->>HTTP: GET node-conf/boot-mode
    R->>HTTP: GET node-conf/public.pem
    HTTP-->>R: all secrets/config
    R->>R: provision EEPROM:
    Note over R: - server public.pem (verify boot.sig)<br/>- SSH pubkey certificate (node auth)<br/>- SSH entrypoint host keys (server auth)<br/>- vpnmac, entrypoints, boot mode
    Note over R: board is now an enrolled VPN node
```

Notes:
- On re-enrollment (e.g. EEPROM was reset / `rpi-5-sd-recovery.tar.gz`), the
  stored SSH certificate is simply updated (`UPDATE vpnauth`), keeping the
  same `vpnmac`.
- The EEPROM has no TPM; the secrets are readable by anyone with a shell on
  the node. Mitigation: the WALT image for RPi5 only allows remote login from
  the WALT server, so secrets are only exposed to WALT users
  (`processes/main/vpn.py` header comment, `vpn-security.md`).
- Changes in VPN settings (entrypoint, boot-mode) cause the board to
  **reflash its EEPROM automatically on next boot**.

## 4. Normal (subsequent) VPN boot over the SSH tunnel

Sequence for an enrolled node, subsequent boots, **VPN path**:

```mermaid
sequenceDiagram
    autonumber
    participant R as "RPi5 firmware"
    participant IM as "initramfs (from boot.img)"
    participant EP as "SSH/HTTP entrypoint"
    participant HTTP as "walt-server-httpd"
    participant TUN as "SSH tunnel endpoint<br/>(walt-server-vpn-endpoint)"
    participant NB as "network boot<br/>(fake-ipxe / NFS / DHCP)"

    R->>R: power-on, u-boot/firmware
    R->>EP: HTTP boot: GET boot.img + boot.sig
    EP->>HTTP: served /walt-vpn/per-ip/<ip>/
    HTTP-->>R: boot.img + boot.sig
    R->>R: firmware verifies boot.sig<br/>with EEPROM public.pem ✓
    R->>IM: chain into kernel + initramfs

    IM->>EP: SSH connect to entrypoint<br/>(auth: node SSH cert, verify: entrypoint host keys)
    EP->>TUN: walt-vpn@server endpoint<br/>(forced command walt-server-vpn-endpoint)
    TUN-->>IM: SSH tunnel established<br/>(virtual network iface at each end)
    Note over IM,TUN: tunnel = encrypted pipe, node continues WalT<br/>network boot procedure through it

    IM->>NB: DHCP through the tunnel
    NB-->>IM: ip / netmask / next-server
    IM->>NB: fake-TFTP fetch over tunnel (start.ipxe → kernel, dtb, initrd)
    IM->>NB: NFS mount root filesystem over the tunnel
    NB-->>IM: /bin/walt-init (regular WalT boot)
    Note over IM: node now runs the WALT OS image
```

- For a node booting **on `walt-net`**, the HTTP entrypoint may not be
  reachable (unless `netsetup=NAT`); the server catches the HTTP boot traffic
  via the `WALT-DNAT` firewall rules and handles it locally.
- Even on `walt-net`, an SSH connection is still attempted to
  `walt-vpn@server.walt` to verify the server is legitimate (guards against a
  crafted network named "walt").

## 5. Boot-mode decision & EEPROM reflash (activity)

What the board does regarding which boot procedure to allow, and when it
updates its EEPROM:

```mermaid
flowchart TD
    A["Power on"] --> B["Read boot mode from EEPROM"]
    B --> C{"loading... VPN boot enabled?<br/>(= boot mode from server conf)"}

    C -- "permissive" --> D["Try VPN HTTP/SSH boot"]
    D --> E{"succeeded?"}
    E -- yes --> F["Boot via VPN tunnel"]
    E -- no --> G["Try unsecure TFTP boot"]
    G --> H{"succeeded?"}
    H -- yes --> I["Boot via TFTP (walt-net)"]
    H -- no --> J["Try OS from SD card"]
    J --> K["Boot from SD card"]

    C -- "enforced" --> D2["Try VPN HTTP/SSH boot (only)"]
    D2 --> E2{"succeeded?"}
    E2 -- yes --> F2["Boot via VPN tunnel"]
    E2 -- no --> L["Halt / no boot<br/>(no fallback)"]

    M["VPN settings changed on server"] --> N["On next boot: node reflashes its EEPROM<br/>to apply new entrypoints / boot mode"]
```

Notes:
- **enforced**: only the VPN procedure is allowed (recommended for public /
  untrusted locations).
- **permissive**: VPN → TFTP → SD-card fallback.
- Regardless of mode, the board reflashes its EEPROM to reflect any VPN
  settings change.
- EEPROM can always be reset out-of-band with an SD card +
  `rpi-5-sd-recovery.tar.gz`, returning the board to a "new / unenrolled"
  state.
